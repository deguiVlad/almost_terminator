# Фокусировка: объекты, руки, или и то и другое

Полноценное решение для удержания цели в поле зрения камеры головы робота
TienKung (nssr-sim, ROS 2 Humble). Пакет: [`focus_tracking/`](../focus_tracking).

Документация разбита на две части: **математика** (этот файл) и
**архитектура нод** (следующий раздел + README пакета).

---

## 1. Математика слежения за объектом (камера → голова)

### Дано

- пиксель цели `(u, v)` — центр bounding box/blob на изображении;
- глубина `d` в этой точке с `/cam_head/depth/image_raw` (16UC1, мм);
- интринсики `fx, fy, cx, cy` из `/cam_head/color/camera_info` (матрица K).

### Шаг 1. Обратная проекция (pinhole model)

```
X = (u − cx) · d / fx
Y = (v − cy) · d / fy
Z = d
```

Точка `P_cam = (X, Y, Z)` в системе координат `camera_head_link`
(оптическая: x вправо, y вниз, z вперёд).

### Шаг 2. Углы визирования

```
yaw   = atan2(X, Z)
pitch = atan2(−Y, sqrt(X² + Z²))      // точная сферическая; упрощённо atan2(−Y, Z) при малых углах
```

Знак минуса у Y: ось Y камеры направлена вниз, а положительный `head_pitch`
в симуляторе — кивок вниз (`docs/INTERFACES.md`, мотор 2 «плюс вниз» — конвенция
проверяется по `/head/status` при первом запуске).

### Шаг 3. Deadzone против шума детекции

Ошибка переводится в пиксели и сравнивается с порогом:

```
e_yaw = yaw_target − yaw_cur,   e_pitch = pitch_target − pitch_cur
err_px = hypot(e_yaw·fx, e_pitch·fy)
|err| < ε_px (≈20 px)  ⇒  команда = текущая поза (моторы молчат)
```

Смысл: шум позиции blob ±5–10 px не должен расшатывать привод; цель
«считается достигнутой» в области, а не в точке.

### Шаг 4. Сглаживание (LPF первого порядка)

```
q_tgt[k] = α·q_meas[k] + (1 − α)·q_tgt[k−1],   α ≈ 0.5
```

Дискретный фильтр с постоянной времени τ ≈ Δt·(1−α)/α ≈ 0.05 c при 20 Гц.
Гасит скачки детектора, вносит фазовое запаздывание ~τ — при неподвижной цели безвредно.

### Шаг 5. Ограничения и отказоустойчивость

```
q_cmd = clamp(q_tgt, q_min, q_max)          // yaw ∈ [−1.57, 1.57], pitch ∈ [−0.44, 0.44]
spd ≤ 0.8 рад/с                              // лимит привода в симе и на реальном роботе
нет цели target_timeout_s                    // возврат в нейтраль (0, 0)
```

### Устойчивость контура

Растение «команда позиции → угол» в симуляторе — ПД-привод с запаздыванием
рендера/физики τ_d ≈ 0.1–0.2 c. Контур «камера→голова» это чистый релейный
П-цикл с большим усилением (ошибка в углах = ошибка цели), поэтому:

- устойчиво при `smoothing α` таком, что effective bandwidth < 1/(4·τ_d);
  α = 0.3…0.5 при 20 Гц — проверочный диапазон;
- deadzone превращает замкнутый контур в «ловлю с гистерезисом»: между
  переключениями мотора энергия шума не проходит в движение;
- для подвижной цели добавляется линейная экстраполяция
  `P̂(t+Δ) = P(t) + V̇·Δ`, где `V = LPF((P[k]−P[k−1])/Δt)` (параметр lead_gain в head_focus_node).

## 2. Математика слежения за рукой через TF

Позиция собственной кисти известна из кинематики — зрение не нужно вовсе,
нужен только правильный запрос преобразования координат.

### Шаг 1. Запрос трансформа (TF2)

```
T = lookupTransform("camera_head_link", "wrist_roll_{l,r}_link", now)
p_cam = T.transform((0,0,0))            // начало системы координат запястья
```

Цепочка кадров строится автоматически из URDF + `/joint_states`:
`pelvis → torso → head_yaw → head_pitch → camera_head_link ← wrist_pitch ← … ← shoulder`
(дерево идёт от pelvis; обратный ход TF инвертирует матрицу 4×4):

```
T_A←B = (T_B←A)⁻¹ = [ Rᵀ | −Rᵀ·t ; 0 0 0 1 ]
```

### Шаг 2. Frustum test (видима ли рука)

```
видима ⇔ Z > z_near  ∧  |X| ≤ Z·tan(hfov/2)  ∧  |Y| ≤ Z·tan(vfov/2)
tan(hfov/2) = cx/fx,  tan(vfov/2) = cy/fy   // прямо из интринсиков
```

### Шаг 3. Проекция в пиксели (для оверлеев/отладки)

```
u = fx·X/Z + cx,   v = fy·Y/Z + cy
```

Прямая задача (3D→px) вместо обратной для объекта — потому что рука уже 3D-известна.

### Шаг 4. Смещение точки удержания

Если держать руку в центре кадра, она загораживает объект. Задаём якорь
`(cx + Δx, cy + Δy)`, например (+150, +100) px — нижний правый квадрант.
В угловой форме эквивалентно:

```
yaw_target  = atan2(X, Z) + Δx/fx
pitch_target = atan2(−Y, hypot(X,Z)) + Δy/fy
```

### Шаг 5. Компенсация собственного движения

Голова крутится → камера движется → `p_cam` руки меняется даже при неподвижной
руке. Это корректная обратная связь: единственная стационарная точка контура —
«рука в якоре кадра», она и является целью, никаких доп. мер не нужно.
Второй эффект: TF-запрос берётся на текущем времени, а команда придёт через
Δt ≈ 50 мс — за это голова успевает повернуться на ω·Δt ≤ 0.04 рад. При
deadzone 20 px (≈0.025 рад) ошибка меньше зоны нечувствительности — компенсация
скорости не требуется; при желании добавляется упреждение `+ω_head·Δt`.

### Шаг 6. Режим BOTH — одна визирная ось на две цели

Минимизируем взвешенную сумму квадратов угловых расстояний до двух целей:

```
J(q) = w_obj·‖θ(q) − θ_obj‖² + w_hand·‖θ(q) − θ_hand‖²
```

В малых углах `θ(q)` линейна по q ⇒ решение — взвешенное среднее:

```
q* = (w_obj·q_obj + w_hand·q_hand) / (w_obj + w_hand)
```

Веса — логика приоритетов: поиск объекта (w_obj=1, w_hand=0.3) → контроль хвата
после касания по `/arm_6dof_*` (w_hand↑). Реализовано в focus_controller_node.

## 3. Структура нод: языки и зависимости

```
                      ┌──────────────────────────┐
 /cam_head/{color,    │ object_detector_node     │──▶ /focus/target   ──┐
 depth}/image_raw ───▶│ Python: rclpy+cv2+numpy  │   PoseStamped        │
 /sim/task            └──────────────────────────┘   (camera_head_link) │
                      ┌──────────────────────────┐                       ▼
 /tf ← /joint_states ▶│ hand_tracker_node        │──▶ /focus/hand  ┌───────────────┐
 (robot_state_pub)    │ C++: rclcpp+tf2_ros      │                 │ focus_        │──▶ /head/cmd_pos
                      └──────────────────────────┘                 │ controller    │    (20 Гц)
                                                                   │ C++: rclcpp   │
 /head/status ─────────────────────────────────────────────────────▶│ (ex-head_     │
                                                                    │  focus_node)  │
                                                                    └───────────────┘
```

| Нода | Язык | Вход | Выход | Зависимости | Почему так |
|---|---|---|---|---|---|
| `object_detector_node.py` | Python (rclpy) | color+depth+camera_info; сервис `/focus/detect` | `/focus/target` | `rclpy, cv2 (opencv-python), numpy, message_filters, sensor_msgs, geometry_msgs, focus_tracking/srv/DetectObjects` | CV/ML-экосистема; 640×360 HSV-детектор ~5 мс/кадр на CPU — частота не критична |
| `hand_tracker_node.cpp` | C++ (rclcpp) | TF2 (`/tf`,`/tf_static`), camera_info | `/focus/hand`, `/focus/hand_visible` | `rclcpp, tf2_ros, tf2_geometry_msgs, geometry_msgs, sensor_msgs, std_msgs, std_srvs` | 50 Гц, нулевой GC-джиттер, чистая математика матриц — vision не нужен |
| `focus_controller_node.cpp` | C++ (rclcpp) | `/focus/target`, `/focus/hand`, `/head/status`, camera_info | `/head/cmd_pos` | `rclcpp, bodyctrl_msgs, geometry_msgs, sensor_msgs, std_srvs` | развитие готового `head_focus_node`; единый интерфейс цели ⇒ математика п.1–2 идентична для объекта и руки |

Архитектурное решение, делающее систему «полноценной»: **все источники целей
публикуют один тип `geometry_msgs/PoseStamped` в одной рамке
`camera_head_link`**. Контроллеру безразлично, откуда пришла цель — объект,
левая рука, правая рука или человек; добавить новый источник = написать ещё
одну ноду-паблишер, не трогая контроллер.

### Ручной выбор цели: список объектов и фокусировка по id/названию

Детектор держит последний синхронизированный RGB-D кадр и умеет отвечать на
запрос оператора — сервис `focus_tracking/srv/DetectObjects` (`/focus/detect`):

```
string select_name   # 'red' | 'green' | ... ; '' = не выбирать по имени
uint8  select_id     # sticky id из ответа; 0 = не выбирать по id (приоритет у select_name)
---
string[] names       # имена объектов, отсортированы по возрастанию sticky id
uint8[] ids          # id в порядке обнаружения (не пересортировываются между кадрами)
float64[] areas_px   # площадь в пикселях
geometry_msgs/PoseStamped[] targets  # 3D-позиции в camera_head_link
bool selected_ok
string message       # человекочитаемый статус
```

Алгоритм детекции для списка: по каждому именованному HSV-окну строится маска
(красный — склейка двух диапазонов, тон огибает 0), морфология OPEN 5×5,
largest connected component.

**Sticky ID (порядок обнаружения, закрепление).** Id присваивается объекту при
первом появлении и больше не меняется: первый замеченный blob получает id=1,
следующий новый — id=2 и т.д. Никакой пересортировки по площади и смещения
номеров между кадрами нет. Соответствие «blob кадра ↔ объект» выполняется
жадным nearest-neighbour по 3D-позиции в рамке камеры: если blob находится
ближе `match_radius_m` (по умолчанию 0.15 м) к последней позиции активного
track и этот track ещё не занят другим blob текущего кадра — id сохраняется;
иначе объект признаётся новым и получает следующий номер монотонного счётчика
(`next_id`, освобождённые номера НЕ переиспользуются). Track удаляется только
если объект не виден дольше `ttl_s` (5 с); ответ сервиса при запросе невидимого
id перечисляет закреплённые номера. Порядок в полях ответа (`names/ids/targets`)
— по возрастанию id, что стабильно от кадра к кадру. Вызов без `select_*`
возвращает список и **не** меняет цель; вызов с `select_name`/`select_id`
публикует выбранную позицию в `/focus/target` (pinhole-проекция как в п.1).
Параметр `auto_select:=false` полностью отдаёт публикацию цели под управление
оператора.

```bash
ros2 service call /focus/detect focus_tracking/srv/DetectObjects                       # список
ros2 service call /focus/detect focus_tracking/srv/DetectObjects "{select_name: red}"   # фокус по имени
ros2 service call /focus/detect focus_tracking/srv/DetectObjects "{select_id: 3}"       # фокус по id
```

### Сборка и запуск

```bash
cd <ws> && colcon build --packages-select focus_tracking
ros2 launch focus_tracking focus.launch.py source:=both hand:=right
# режимы на лету:
ros2 service call /focus/set_mode std_srvs/srv/SetBool "{data: false}"   # IDLE
ros2 service call /focus/set_hand std_srvs/srv/SetBool "{data: true}"    # правая рука
```

### Отличия от реального робота (учтены)

- скорость моторов ограничена 0.8 рад/с — команды `spd` ставятся ≤0.7;
- ПД-привод даёт недолёт — для головы несущественно (deadzone перестроится),
  для руки в контуре захвата нужен внешний цикл по `/joint_states`;
- `use_sim_time:=true` обязательно (время из `/clock`).

## 4. Математика сопровождения рукой (hand_follow, режим «захват»)

Голова цель **видит**; рука должна в неё **дойти**. Тот же `PoseStamped`-контракт,
но контур замыкается через кинематику руки, а не головы.

### Шаг 1. Перенос цели из рамки камеры в рамку базы

Цель `(X,Y,Z)` задана в `camera_head_link`, IK требует `base_link`(=`pelvis`):

```
p_base = T(pelvis ← camera_head_link) · p_cam        // TF2 lookupTransform, одна матрица 4×4
T(pelvis←cam) = [ R | t ],  p_base = R·p_cam + t
```

R и t зависят от живых суставов head_yaw/head_pitch — TF пересчитывает их сам
из `/joint_states`. Важный эффект: когда голова следит за объектом, оптическая
ось смотрит на объект ⇒ вектор `t` почти сонаправлен с целью, то есть после
переноса `p_base` лежит примерно на визирной оси на дистанции ‖цели‖ — это
естественная «точка перед собой», из которой вычитается смещение подхода.

### Шаг 2. Точка подхода (avoid collision offset)

Хватывать «в центр объекта» нельзя — пальцы упрутся в стол/соседей. Цель для
запястья:

```
p_grip = p_base + n̂ · (r_obj + r_hand) ,   n̂ = нормаль захвата (обычно сверху −z или сбоку)
```

В симуляторе объекты лежат на столе ⇒ штатный вариант `n̂ = (0,0,−1)` c
запасом ~5–8 см: кисть встаёт над центром объекта, пальцы смыкаются снизу.

### Шаг 3. IK и замкнутый контур

Сервис IK блока arm (уже есть в API) даёт `q_ik = f⁻¹(p_grip, R_wrist)`. Но
приводы — ПД с недолётом до 15 % ⇒ разомкнутой команды мало. Итеративная коррекция
по обратной связи (аналог DLS-шага, но без пересчёта Якобиана):

```
Δp[k]   = p_grip − FK(q_meas[k])          // ошибка по /arm/status (или TF pelvis→wrist)
q_cmd[k+1] = q_ik + J⁺(q_meas[k]) · Kp·Δp[k],   Kp ≈ 0.5…1.0, шаг ≤ 0.1 рад/цикл
```

где `J⁺` — псевдообратный Якобиан (сервис IK отдаёт его при запросе; либо
повторные вызовы IK с смешением цели: `p_target += Kp·Δp` — проще и эквивалентно
для малых Δp). Сходимость линейная: ‖Δp[k]‖ ≤ (1−Kp)ᵏ‖Δp[0]‖ при Kp≤1.

### Шаг 4. Хват по силе

Триггер контакта — датчик запястья `/arm_6dof_{l,r}` (WrenchStamped, вес кисти
вычтен):

```
‖F_xy‖ > F_th (≈3–5 Н)  ∧  z-компонента момента растёт   ⇒  контакт
→ пальцы: /inspire_hand/ctrl/{side}_hand position: [0.2,…,0.2, 0.5, 0.2]
→ предел силы: /inspire_hand/set_force {force: 0.3}       // ~300 г, чтобы не раздавить
```

После захвата `focus_controller` переключает веса both-режима (w_hand↑), чтобы
контролировать удержание объекта в кадре вместе с кулаком.

### Шаг 5. Ограничения совместности

Все суставы руки движутся одним кадром `/arm/cmd_pos`; лимит 0.8 рад/с на мотор.
Оценка времени перехода: worst-case перестановка ~π рад ⇒ ≥ 4 c. Планировщик
простой: движение к `p_grip` выполняется до триггера хвата, прерывается только
потерей цели (таймаут `/focus/target`).

Реализация: `hand_follow_node.cpp` — прямое развитие этой математики поверх
готового `zahvat.cpp` (там уже есть цикл cmd_pos→status); в MVP не входит,
формулы выше — спецификация.
